# Claude build prompt: OpenBao vs HashiCorp Vault: What's the Difference?

A "should we move from Vault?" checklist builder for Claude Code. Read-only: it never connects to Vault or OpenBao; it reads exported settings and writes one report. Rules checked against openbao.org on 2026-11-06 (OpenBao v2.7.2). Not run by us.

Use this in Claude Code (Pro or higher), in an empty test folder. Start in plan mode.

Goal: build a read-only "should we move from Vault to OpenBao?" checklist from exported Vault settings, without touching any Vault or OpenBao server.
Inputs, all in this folder, from a test or staging Vault (the video's inventory.sh in Full code makes the last four), with every token, key and password replaced by XXXX before you start: vault-config.hcl (the server config file), secrets-list.json (output of vault secrets list -format=json), auth-list.json (output of vault auth list -format=json), status.txt (output of vault status) and version.txt (output of vault version). If I don't have them, first write small fake versions of all five, with an awskms seal, a file storage stanza, disable_mlock = true, an aws secrets engine and a namespace, and use those.
Steps, in order:
1. Tell me which files you'll open and what you'll write, and wait for my yes. Never run vault, bao, curl or docker, and never connect to any server.
2. Scan every input for anything that still looks like a real secret (strings starting hvs., hvb., hvr., s., b. or r. followed by more than 8 characters, or long base64 strings). If you find one, stop, show only the file name and line number, and ask me to redact it.
3. Version: compare version.txt with the migration guide at openbao.org/docs/guides/migration. Mark 1.14.1 Community as tested, older as "upgrade to 1.14.1 first", newer as "untested: OpenBao makes no guarantees about storage compatibility", and any "+ent" version as "Enterprise: not tested".
4. Config: flag disable_mlock (remove it; OpenBao does not use mlock since 2.0.0), storage "file" (removed from the OpenBao server in 2.7.0; move the data first, for example with bao operator migrate, which still accepts file as a source until 2.8.0), any storage other than raft, postgresql or pebbledb (check openbao.org/docs/configuration/storage), and each seal type: shamir, static, transit and kmip are built in; awskms, azurekeyvault, gcpckms, alicloudkms, ocikms, pkcs11 and others need a plugin from github.com/openbao/openbao-plugins (check openbao.org/docs/configuration/seal).
5. Mounts: for every entry in secrets-list.json and auth-list.json, check whether OpenBao documents that type under openbao.org/docs/secrets or openbao.org/docs/auth, or lists it as a plugin in the github.com/openbao/openbao-plugins README (for example aws, azure and gcp). Mark each as built in, plugin needed, or not found, and note the guide's warning that a mount whose plugin is missing is skipped at startup. Flag agent-registry, which Vault 2.0 and later add by default.
6. Enterprise features: flag namespaces, replication, Sentinel policies, control groups, performance standbys, HSM seals and Secrets Sync if they appear, and for each say whether openbao.org documents an equivalent (namespaces and control groups: yes, written separately; replication, Sentinel, Secrets Sync: no page found), quoting the page.
7. Clients: remind me that new OpenBao tokens look like s.random, not hvs.random, and list any script in this folder that checks for hvs. Note that VAULT_ environment variables still work in OpenBao when no BAO_ one is set (openbao.org/docs/commands), and list every VAULT_ variable the scripts use.
8. Write move-checklist.md: a table with each item, the result (ready, needs work, blocker), the fix and the openbao.org page it comes from, then a one-paragraph verdict. Write nothing else.
Safety: this folder and test data only, read-only. No network calls except reading openbao.org pages if I allow it, no installs, never real secrets. Stop and ask me before running anything that changes data.
Output: move-checklist.md and a three-line summary.
